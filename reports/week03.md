# Week 03 — Ограничения целостности БД салона красоты

**Проект:** `tursunova-db`  
**Схема:** `beauty`  
**Миграция:** `migrations/03_constraints.sql`

## 1. Внешние ключи и ON DELETE

| Внешний ключ | Связь | ON DELETE | Обоснование |
|---|---|---|---|
| `fk_salons_owner` | `salons.owner_id → users.id` | `SET NULL` | Удаление аккаунта владельца не должно удалять сам салон из каталога. |
| `fk_services_category` | `services.category_id → categories.id` | `SET NULL` | При удалении категории услуга остаётся в каталоге и может быть отнесена к другой категории. |
| `fk_user_roles_user` | `user_roles.user_id → users.id` | `CASCADE` | Связи ролей — зависимые записи; после удаления пользователя они не нужны. |
| `fk_user_roles_role` | `user_roles.role_id → roles.id` | `RESTRICT` | Нельзя удалять роль, пока она назначена пользователям. |
| `fk_masters_user` | `masters.user_id → users.id` | `RESTRICT` | Профиль мастера связан с аккаунтом; удаление аккаунта должно быть сначала обработано явно. |
| `fk_masters_salon` | `masters.salon_id → salons.id` | `RESTRICT` | Нельзя удалить салон, пока в нём зарегистрированы мастера. |
| `fk_master_services_master` | `master_services.master_id → masters.id` | `CASCADE` | Связи мастер–услуга зависят от существования мастера. |
| `fk_master_services_service` | `master_services.service_id → services.id` | `RESTRICT` | Нельзя удалять услугу из каталога, пока она назначена мастерам. |
| `fk_working_schedules_master` | `working_schedules.master_id → masters.id` | `CASCADE` | График не существует отдельно от мастера. |
| `fk_appointments_client` | `appointments.client_id → users.id` | `RESTRICT` | Сохранение истории записей важнее автоматического удаления клиента. |
| `fk_appointments_master` | `appointments.master_id → masters.id` | `RESTRICT` | Нельзя удалить мастера, на которого ссылается история записей. |
| `fk_appointments_service` | `appointments.service_id → services.id` | `RESTRICT` | Услуга должна оставаться в каталоге, пока на неё ссылаются записи. |
| `fk_reviews_appointment` | `reviews.appointment_id → appointments.id` | `CASCADE` | Отзыв — зависимая запись конкретного посещения и удаляется вместе с ним. |

### Обоснование трёх выборов ON DELETE

1. `salons.owner_id ON DELETE SET NULL`: при удалении учётной записи владельца сведения о салоне сохраняются, а ссылка на владельца очищается.
2. `user_roles.user_id ON DELETE CASCADE`: после удаления пользователя его строки назначения ролей не имеют смысла и могут удаляться автоматически.
3. `appointments.master_id ON DELETE RESTRICT`: история записей должна сохраняться; мастер не может быть удалён, пока на него ссылаются записи.

## 2. CHECK-ограничения

| Ограничение | Бизнес-правило |
|---|---|
| `ck_categories_name_length` | Название категории должно содержать от 2 до 80 символов после удаления пробелов по краям. |
| `ck_services_name_length` | Название услуги должно содержать от 2 до 120 символов. |
| `ck_salons_name_length` | Название салона должно содержать от 2 до 160 символов. |
| `ck_salons_address_length` | Адрес салона должен содержать от 5 до 250 символов. |
| `ck_salons_phone_format` | Если телефон указан, он должен содержать цифры и допустимые разделители; допускается начальный `+`. |
| `ck_users_phone_format` | Телефон пользователя должен соответствовать формату международного/локального номера с допустимыми разделителями. |
| `ck_users_email_format` | Email пользователя, если указан, должен иметь базовую структуру `name@domain.tld`. |
| `ck_masters_specialization_length` | Указанная специализация мастера должна содержать от 2 до 120 символов. |
| `ck_working_schedules_business_hours` | По правилу проекта график салона находится в диапазоне 06:00–23:00. Этот диапазон можно поменять, если бизнес-модель предполагает другие часы. |
| `ck_appointments_duration` | Запись на услугу длится не менее 10 минут и не более 8 часов. |
| `ck_reviews_comment_length` | Если комментарий к отзыву указан, он должен содержать от 5 до 2000 символов после удаления пробелов по краям. |

В миграции также сохранены CHECK-ограничения, заданные ранее: неотрицательная цена, положительная длительность услуги мастера, корректный интервал графика и рейтинг от 1 до 5.

## 3. UNIQUE и ENUM

- `uq_users_phone UNIQUE (phone)` — номер телефона не может принадлежать двум пользовательским аккаунтам.
- `uq_masters_user_salon UNIQUE (user_id, salon_id)` — один пользователь не может иметь два профиля мастера в одном салоне; это составное ограничение UNIQUE.
- Создан ENUM `beauty.appointment_status` со значениями `booked`, `completed`, `cancelled`; столбец `appointments.status` использует этот тип и по умолчанию получает `booked`.

## 4. Негативные тесты

Файл: `queries/week03_negative.sql`. Каждый негативный INSERT должен завершиться ожидаемой ошибкой. Скрипт использует savepoint, чтобы после ожидаемой ошибки продолжить остальные тесты, а в конце откатывает транзакцию, не оставляя тестовых данных.

| № | Что проверяется | Ожидаемый SQLSTATE | Фактический результат |
|---:|---|---|---|
| 1 | Некорректный email пользователя | `23514` — `check_violation` | **Заполнить после запуска:** вставить фактическую строку `ERROR` из лога. |
| 2 | Дублирующийся номер телефона | `23505` — `unique_violation` | **Заполнить после запуска:** вставить фактическую строку `ERROR` из лога. |
| 3 | Некорректный телефон салона | `23514` — `check_violation` | **Заполнить после запуска:** вставить фактическую строку `ERROR` из лога. |
| 4 | Несуществующий владелец салона | `23503` — `foreign_key_violation` | **Заполнить после запуска:** вставить фактическую строку `ERROR` из лога. |
| 5 | Статус записи `pending`, которого нет в ENUM | `22P02` — `invalid_text_representation` | **Заполнить после запуска:** вставить фактическую строку `ERROR` из лога. |

### Фактический вывод PostgreSQL

После запуска тестов добавь сюда фактический вывод из `reports/week03_negative_output.txt` — как минимум строку ошибки для каждого из пяти тестов. Не заменяй фактические ошибки ожидаемыми результатами из таблицы выше.

## 5. Команды запуска и проверка

Миграции выполняются по порядку в новой/пустой учебной базе: `01_init.sql`, затем `02_schema.sql`, затем `03_constraints.sql`. **`01_init.sql` содержит `DROP SCHEMA beauty CASCADE` и удаляет текущую схему, поэтому в уже существующей базе его нельзя запускать повторно без необходимости сброса данных.** Если `01` и `02` уже применены, запускай только `03_constraints.sql`.

Негативные тесты запускаются без `ON_ERROR_STOP=1`, поскольку ожидаемые ошибки должны отображаться, а следующие тесты должны продолжить выполняться.
